    Why it exists

    Allowed is not the same as intended.

    Agents chain many reasoning steps and tool calls between a user's request and a real-world effect. Permission checks alone miss three things.

    “Is this still what they asked for?”

    “Investigate why production is slow” quietly becomes “restart the production database.” Nobody revoked authority; the plan just wandered.

    “The tool is allowed. Is the amount?”

    issue_refund() is a permitted tool. Refunding $850 against a $500 authorization is not a permitted decision, even though the call would succeed.

    “What is it doing, and can I stop it?”

    Long-running agents act for minutes at a time with no live view of what they are about to do, and no clean way to pause them.

    Agentic Sidecar answers all three at the tool boundary: it checks each proposed action against policy, risk, the original intent and the budget, then allows it, pauses it for a human, or stops it before it runs.

    Where it sits

    The agent acts. The Sidecar decides.

    Agentic Sidecar attaches to the loop you already run, at the moment a decision is about to become an action. It never owns the task, never becomes a second worker, and never executes the plan.

    What it does

    A checkpoint before every call.

    Turn on only the checks you need. Policy, risk, intent and budget are plain rules with no model calls. Plan review, Critic and Judge are opt-in when you want a second opinion.

    Policy Advisorexample
    PolicyAdvisor([
    PolicyRule(tool="delete_*", effect="deny"),
    PolicyRule(tool="read_*", effect="allow"),
])

delete_customer_record(...)
→ BLOCK  Matched policy rule tool='delete_*' -> effect=deny

    Rules · no model

    Policy Advisor

    Ordered allow and deny rules matched on tool names with glob patterns. It is the cheapest check, so it runs first. Load rules from YAML or code.

    Risk Evaluatorexample
    default: LOW
rules:
  - tool: "issue_refund"
    arg_name: amount
    arg_op: gt
    arg_value: 500
    risk: HIGH

issue_refund(amount=850)
→ BLOCK  risk=HIGH (risk >= block threshold 'HIGH')

    Rules · no model

    Risk Evaluator

    Classifies each action as LOW, MEDIUM or HIGH from the tool and its arguments, and intervenes when risk reaches the threshold you set.

    Intent Guardianexample
    IntentEnvelope(
    goal="Refund order A100 up to $500",
    constraints={"maximum_refund": 500},
)

issue_refund("A100", 850)
→ BLOCK  'amount'=850 on 'issue_refund' violates
         constraint 'maximum_refund' (must be lte 500)

    Rules · no model

    Intent Guardian

    Carries what the user actually asked for, and binds its limits to tool arguments. The refund tool stays allowed; the $850 refund does not.

    Budget Guardianexample
    budget = BudgetGuardian(max_cost=5.00, max_tokens=10_000)
budget.record_invocation(cost=5.00, tokens=1200)

read_order()
→ PAUSE  Budget Guardian: cost $5.0000 >= $5.0000

    Rules · no model

    Budget Guardian

    Per-task cost and token ceilings. Judge usage is counted automatically; once spend crosses the limit, the next call pauses for a human.

    Authority and scoped context

    Explicit tool bindings, narrowed delegation and revocation that follows the chain. Shared or Exclusive context per agent, with guardrails that always apply.

    Operating modes

    Observe first, then govern.

    Start by recording what the Sidecar would decide, with nothing blocked. When the verdicts look right, switch the same configuration to Govern.

    Observe mode

    Default

    Record every verdict

    Each proposed call is evaluated and recorded with its full decision payload, but wrapped tools always execute. Nothing in your agent changes behavior.

    Tool calls
    Always execute
    Verdicts
    Computed and recorded in the audit trail
    Setting
    mode="observe"

    Best for: first deployments, shadow auditing and tuning your rules.

    Govern mode

    Enforces

    Enforce the boundary

    ALLOW and WARN proceed. BLOCK raises SidecarBlockedError before the tool runs. PAUSE and ESCALATE ask a human, and CHALLENGE and REPLAN hand control back to your agent loop.

    Tool calls
    Only ALLOW and WARN execute
    If it fails
    You choose: fail_closed or fail_open
    Setting
    mode="govern"

    Best for: production, money movement and destructive tools.

    The decision gate

    Seven outcomes, one gate.

    Policy asks “are you permitted?”, risk asks “how dangerous is this?”, and intent asks “is this what the human asked for?”. The decision gate turns their answers into one outcome.

    • ALLOWThe action runs.
    • WARNThe action runs, and the warning is recorded.
    • CHALLENGEControl returns to the agent with the objection, before anything runs.
    • REPLANThe plan needs to change. Control returns to the agent loop.
    • PAUSEWaits for a person, for example when a budget ceiling is reached.
    • ESCALATENeeds human approval before it can run.
    • BLOCKNever runs. A blocked action cannot be approved.

    Live operations

    Watch it live. Stop it any time.

    Every proposal, decision, dispatch and completion lands in an immutable task journal. Follow it from the terminal or the built-in Control Room, and pause, stop, approve or change the intent while the agent runs.

    • agentic-sidecar status --followLive narration of the running task
    • agentic-sidecar control pauseAlso resume, stop, restart and replan
    • agentic-sidecar approve ID approve_onceOr reject, modify_intent, stop_agent, replan

    The operator server listens on 127.0.0.1 only, and every request needs a bearer token. Reader tokens see a redacted summary and can't control anything.

    How it works

    Govern your first tool in four steps.

    No model or API key needed. The example below uses plain Python functions; swap in your framework's adapter when you're ready.

    1. 1

      Install

      The core package needs Python 3.10 or later. Add an extra such as [langgraph] for your framework.

      pip install agentic-sidecar
    2. 2

      State the intent

      Describe what the user asked for, and bind its limits to the tool arguments that matter.

      constraints={"maximum_refund": 500}
    3. 3

      Attach to your tools

      Wrap the tool list your agent already uses. The tools themselves don't change.

      (refund,) = attach(sidecar, [issue_refund])
    4. 4

      Choose a mode

      Start in Observe. Switch to Govern and handle blocked or suspended calls in your loop.

      Sidecar(mode="govern", on_sidecar_failure="fail_closed")
    python 
    from agentic_sidecar import Sidecar, SidecarBlockedError
from agentic_sidecar.adapters.langgraph import attach
from agentic_sidecar.intent import ConstraintBinding, IntentEnvelope, IntentGuardian, Requester

def issue_refund(order_id: str, amount: float) -> str:
    """Issue a refund for an order."""
    return f"refunded {amount} for {order_id}"

envelope = IntentEnvelope(
    goal="Refund order A100 up to $500",
    requested_by=Requester(id="support_lead"),
    constraints={"maximum_refund": 500},
)
guardian = IntentGuardian(envelope, [ConstraintBinding(
    constraint="maximum_refund", tool="issue_refund", arg_name="amount", op="lte",
)])
sidecar = Sidecar(
    on_sidecar_failure="fail_closed", mode="govern",
    intent=guardian, roles=["policy", "risk", "intent_guardian"],
)
(refund,) = attach(sidecar, [issue_refund])

print(refund("A100", 120))  # refunded 120 for A100
try:
    refund("A100", 850)
except SidecarBlockedError as exc:
    print(exc.decision.status)  # BLOCK; the refund function was never called

    Multi-agent systems

    Many agents, one set of rules.

    As a task fans out from agent to agent, each hop tends to see only its own sub-task. The Sidecar keeps the original constraints and authority attached, however far the work is delegated.

    Shared and Exclusive scopes

    Since 0.8

    Context and guardrails per task or per agent

    Give every agent in a task the same context and rules, add rules for named agents only, or both. Each agent gets its own Sidecar, history and runtime.

    ScopedSystem(
    system_id="support", task_id="ticket-42",
    agents=["research", "refund"],
    shared=ScopeLayer(guardrails=GuardrailSpec(
        rules=[PolicyRule(tool="delete_*", effect="deny")])),
    exclusive={"refund": ScopeLayer(guardrails=GuardrailSpec(
        rules=[PolicyRule(tool="export_*", effect="deny")]))},
)
research → export_records   ALLOW
refund   → export_records   → BLOCK
anyone   → delete_customer  → BLOCK
    Shared
    Applies to every agent in the task
    Exclusive
    Applies to the agents you name
    Rule
    An exclusive allow never overrides a shared deny

    Task authority

    Since 0.9

    Delegate less. Revoke everything.

    Bind authority to tools, hand a narrower grant to each sub-agent, and revoke the whole chain at once. Checks run at dispatch time, so a revoked grant can't slip through.

    child = parent.delegate(
    agent_id="refund-agent", authority={"refund": True},
)
parent.revoke()   # descendants lose authority too

refund(amount=50)
→ BLOCK  Task authority revoked
    Delegate
    Permissions can only narrow
    Expiry
    A child grant can't outlive its parent
    Stop
    Stopping a task revokes every descendant

    Where this is going: the Intent Envelope is designed to travel with the task across processes and agents, so every hop can answer what was asked, who authorized it, and what limits still apply. It ships today as a candidate IntentTransfer contract.

    FAQ

    Common questions.

    Quick answers about cost, data, models and how the Sidecar fits next to your framework.

    Still have questions? Ask the community on Discord, or open an issue on GitHub. Feature ideas are welcome too.
    Ask on Discord Open an issue ↗
    Is Agentic Sidecar free?

    Yes. It's open source under the MIT license, like every DeepAgentLabs package.

    Does it call an LLM on every action?

    No. Policy, risk, intent and budget checks are deterministic rules with no model calls. Plan review and Critic are heuristics, and a Judge model is only used if you add one and choose its provider, model and token rates.

    Does my data leave my machine?

    The Sidecar runs inside your own process and sends nothing to DeepAgentLabs. If you enable an OpenAI or Anthropic Judge, that provider receives the decisions you send it.

    How is it different from a guardrails library?

    Content guardrails check a single prompt or response. The Sidecar checks a decision, such as a tool call or a plan step, against the intent and context gathered across the whole task.

    Does it replace my agent framework?

    No. It isn't a harness or a multi-agent framework, and it never executes your plan. It attaches to LangGraph, CrewAI, the OpenAI Agents SDK or your own loop at the tool boundary.

    Isn't this what tracing tools do?

    No. Tracing tools like AgenticLens answer “what did the agent do, and why did it fail?” after the fact. The Sidecar answers “should it do this?” while the agent is still running, before the action happens.

    Is it just LLM-as-a-judge?

    No. A Judge model is one optional evaluator inside one module. Most decisions never reach a model: policy, risk, intent and budget are plain rules that run first and cost nothing.

    What happens if the Sidecar itself fails?

    You decide up front. on_sidecar_failure is a required setting: fail_closed blocks the call, fail_open lets it through. See limitations for the details.
